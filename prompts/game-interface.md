# Prompt: Game Interface and Website Adaptation
**For game menus, HUDs, card tables, codex pages, and supporting websites**

Use this prompt to adapt the house style to a game's actual interface. Functional clarity outranks ornament.

---

## COPY FROM HERE

Design a game interface or website under The Estate Codex.

The Codex is a presentation standard, not a fictional setting requirement. Do not add castles, abbeys, aristocrats, lore panels, or historical language to a project unless its source material calls for them.

### First understand the product

Identify:
- The game's genre and core interaction.
- Primary player task on each screen.
- Information the player must see immediately.
- Inputs, states, feedback, and accessibility needs.
- Target resolution, platform, and input method.
- Content that must remain unobstructed.

If the interface is a card game, the cards and playfield are the main event. If it is a puzzle, the board and state feedback are the main event. The Codex must not make a usable game harder to use.

### Apply the house style

Use:
- Cinzel Decorative for selected display headings.
- EB Garamond for body and longer reading.
- Press Start 2P for short technical labels only; it is not a body font.
- Oxblood for primary actions and selected states.
- Parchment and bone for reading surfaces and text.
- Antique gold for borders and limited emphasis.
- Deep evergreen and moss for restrained positive or hover states.
- Stone, iron, and pixel-built ornament where it reinforces grouping.

Use hard borders and deliberate rectangular structure. Ornament should clarify navigation, section boundaries, selected states, or material identity.

### Reject

- Generic SaaS dashboards.
- Floating rounded cards and glass panels.
- Gradient backgrounds or luminous orbs.
- Fake charts, fake statistics, and empty feature cards.
- Excessive ornament inside the play area.
- Animations that hide state or impair input.
- Tiny pixel fonts for long instructions.
- Decorative symbols that resemble functional buttons but do nothing.

### Screen specification

For each screen, define:
1. Purpose.
2. Primary user action.
3. Information hierarchy.
4. Layout zones.
5. Visual register.
6. Typography.
7. Color and state behavior.
8. Ornamental elements.
9. Interaction and feedback.
10. Small-screen or alternate-resolution behavior.

Provide a low-fidelity structural layout before detailed skinning. Do not use visual polish to disguise a broken information hierarchy.

### Deliverables

Return:
- Screen inventory.
- Shared interface rules.
- Individual screen briefs.
- Interaction states.
- Responsive or resolution behavior.
- A copy-ready prompt for any required visual assets.
- A list of practical usability risks.

Do not create an image-generation integration or assume an external API. The result is a design reference or implementation brief unless explicitly asked for code.
